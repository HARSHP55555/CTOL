## 1. Methodology
OptiGraph implements an end-to-end context optimization framework designed to provide LLMs with the minimum sufficient code context needed to answer developer questions accurately without exceeding context token limits.

### Pipeline Stages
1. **Graph Ingestion:** Ingests a canonical code knowledge graph representing repository AST symbols, files, modules, and relationships (`CONTAINS`, `IMPORTS`, `CALLS`, `USES`).
2. **Context Retrieval (Step 4):** Identifies initial seed nodes matching query tokens and performs relationship traversal up to a configured depth of 1, extracting candidate code snippets.
3. **Evidence Ranking (Step 5):** Multi-factor scoring ranks retrieved nodes and snippets based on keyword match quality, graph centrality, traversal proximity, and symbol types.
4. **Budget-Constrained Selection (Step 6):** Dynamically selects top-scoring evidence items, checks snippet overlaps to eliminate redundancy, and ensures total context does not exceed the token budget ceiling.

### Baseline Definitions
- **Baseline 1: Full-Repository Context (Zero-Retrieval Dump):** Counts tokens required to include all available source files in the evaluated repository in full, representing the naive brute-force context stuffing approach.
- **Baseline 2: Whole-File Retrieval (Oracle / Ground-Truth-Assisted):** Identifies relevant files by combining benchmark `expected_files` annotations with retrieved entity files and includes those files in their entirety, without graph snippet pruning. Because it is seeded with ground-truth file targets, it represents an optimistic upper bound on relevance for whole-file retrieval (i.e., zero false positives and zero missed ground-truth files), providing a rigorous, conservative comparison against OptiGraph's snippet pruning.
- **Baseline 3: Step 4 Unoptimized Retrieval:** Includes all retrieved seed nodes, traversed relationship edges, and unpruned extracted snippets prior to rank-based optimization.

### Token Estimation Parity
> [!NOTE]
> All token counts in this report are heuristic estimates generated by `ApproximateTokenEstimator`. The estimator counts whitespace-delimited and punctuation-split tokens with bounds validation and adds structural overhead for line citations (`### File: <path> (lines X-Y)`) and code fences. Identical counting logic is applied across all three baselines and the optimized pipeline.

## 5. Limitations
1. **Token Estimation Approximations:** Token counts are computed using heuristic character and pattern matching (`ApproximateTokenEstimator`). Although internally consistent across all compared methods, exact token numbers will vary slightly with proprietary BPE tokenizers (e.g., GPT-4 `cl100k_base` or Claude).
2. **Fixture Scale Effects & Signed Reductions vs Whole-File Retrieval:** The evaluated sample repository is compact (32 lines across 3 files, totaling 296 source tokens; `src/auth.py` is only 142 tokens). When configured with a generous budget ceiling (250 tokens), OptiGraph has ample budget headroom and intentionally packs relevant graph AST nodes, symbol definitions, and relationship edges into the context package (reaching 240–247 tokens). Because raw single files in this micro-fixture are smaller than the 250-token budget ceiling, OptiGraph's enriched graph context yields signed negative token reductions (-5.7% to -73.9%) relative to single raw files at budget 250. Conversely, under constrained token budgets (e.g., 100 tokens), whole files exceed the budget limit (142 > 100), whereas OptiGraph compresses context to 71–78 tokens, achieving **+45.1% to +53.9% token savings** while strictly honoring the budget ceiling.
3. **Oracle Assistance in Whole-File Baseline:** Whole-file retrieval utilizes benchmark ground-truth `expected_files` annotations to identify relevant files. This oracle assistance guarantees zero false positives and zero false negatives, representing an optimistic upper bound for full-file retrieval.
4. **Fixed Traversal Depth:** The benchmark was executed with traversal depth 1. Higher traversal depths expand candidate context packages and increase the relative token pruning benefit of Step 5/6.
